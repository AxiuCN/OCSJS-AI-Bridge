# 待办与规划

## 已定案

| 决策 | 结论 | 依据 |
|---|---|---|
| 落地形态 | **B**：本仓库新写与既有 `response_service` 同协议的独立服务 | 参考项目只读；形态 A 无法承载可插拔多后端 |
| 技术选型 | **Node.js + TypeScript**，运行期零第三方依赖 | 形态 B 已放弃复用 Python 代码；Node 24 内建 fetch/AbortSignal/node:test |
| 后端范围 | **任意后端可插拔**：Ollama 原生 / OpenAI 兼容 / Responses 平级 | 用户明确要求不局限于本地 Ollama |
| 多后端策略 | **服务端决定**，`/v1/answer` 不新增选择字段 | OCS 只能传 title/options/type |
| 策略钩子 | 用户自写 JS，运行时决定候选链；热重载；异常回退 | 支持时段折扣、临时关闭、互斥使用 |
| 图片题 | OCS 5.x 直传 data URL（主），服务端下载（兼容） | 服务端下载受登录态/防盗链限制 |

## 待定

- 路由策略的默认取值（哪种题型优先走本地、哪种走云端），由实际答案质量决定
- 多后端合并配置的默认形态（是否内置一份 `multi` 示例）
- 是否需要 `probe` 子命令辅助读取 Ollama `capabilities`（可选工具，不在主链路）

## 验收标准

1. OCSJS 端**仅通过题库配置**即可用上所选 AI 后端；本地 Ollama 为必测项之一，在线后端为可选项
2. 原有功能不退化：题型（单选/多选/判断/填空/连线/阅读）、图片题、答案回填格式与既有服务一致
3. 上游不可用 / 无图可读 / 超时 / 候选均无视觉能力等情况，均有明确 `code:0` 报错，不静默返回错误答案；降级过程如实记入 `warnings`
4. 服务在 Windows 与 Linux 上均可运行（至少一端完整验收）
5. 参考项目未被修改

## 已知限制

- 候选链是**串行降级**，不是并行竞速；慢后端会消耗总预算，快的应排在前面
- 一次只跑一套配置（同一端口）；多后端需合并到同一份 config
- 单实例只有一个访问令牌，OCS 侧无法按后端区分
- 各平台答题正误无法自动回传（OCS 无判分接口），因此缓存类功能需要人工反馈或额外脚本
