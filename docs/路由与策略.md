# 路由与策略

## 候选链

`config.jsonc` 的 `routes` 按题型给出候选链，按顺序逐个尝试：

```jsonc
"routes": [
  { "type": "multiple", "backends": ["online-responses", "ollama-local"] },
  { "type": "*",        "backends": ["ollama-local"] }
]
```

- `type` 精确匹配优先，`"*"` 兜底；同一题型命中多条时以第一条为准
- `/v1/answer` **不提供**后端选择字段（OCS 也传不了），选择与降级完全由服务端决定

## 超时预算

- OCS 搜题上限 180s，服务端总预算默认 170s
- 单候选超时 = `min(自身 timeout_seconds, 剩余预算)`，转换为正整数毫秒，保留小数秒配置
- 客户端在发送完整请求体后断开时，也会取消对应的上游任务
- 剩余预算低于 `min_attempt_seconds` 时放弃该候选并说明原因
- 剩余预算不足一半时不再开启思考，把时间留给出答案

## 能力过滤

题目含图时，未声明 `vision: true` 的后端会被跳过并记入 `warnings`；全部候选都不支持视觉则明确报错，不静默猜测。

## 降级分类

| 情况 | 处理 |
|---|---|
| 连接失败 / 超时 / HTTP 错误 / 非 JSON / 缺 answer / 空答案 | 后端级 → 换下一候选，原因写 `warnings` |
| 题目含图但一张都读不出 | 题目级 → 立即 `code:0`，不降级 |
| 候选无视觉能力却遇图片题 | 跳过并记原因 |
| 全部候选失败 | `code:0` 并列出每个候选的失败原因 |

## 策略钩子（可选）

需要按时间、题目特征或临时开关动态决定时，启用用户自写的 JS：

```jsonc
"policy": { "file": "./policy.js", "timeout_ms": 100 }
```

```js
```js
// 与宿主机时区无关的小时取法（服务器不是 UTC+8 时必需）
function hourIn(now, timeZone = "Asia/Shanghai") {
  return Number(
    new Intl.DateTimeFormat("en-US", { timeZone, hour: "numeric", hourCycle: "h23" }).format(now),
  );
}

export function decide(ctx) {
  const hour = hourIn(ctx.now);
  if (ctx.hasImages) return ["deepseek-flash"];
  if (hour >= 22 || hour < 8) return ["qwen-deepseek", "deepseek-flash"];
  if (ctx.questionType === "judgement") return ["ollama-local"];
  return ["deepseek-flash", "ollama-local"];
}
```

- `ctx`：`now` / `questionType` / `hasImages` / `imageCount` / `backendNames` / `defaultOrder`（不含题目文本）
- 返回字符串数组，或 `{ name, timeoutSeconds?, think? }` 数组覆盖单次参数
- 返回 `null` / `undefined` / 空数组 → 回退 `routes` 默认顺序
- **未配置的后端名会被忽略**并记入 `warnings`；若过滤后仍有有效候选则继续使用，全部无效才回退默认顺序
- 文件缺失、脚本抛错、超时、返回值无法解析 → 回退默认并记 `warnings`，不中断答题
- 改文件无需重启（按 mtime 热重载；**内容变但 mtime 未变时仍用缓存**，可用 `touch` 触发）
- 策略只决定候选链；预算、能力过滤、降级仍由路由层保证

**边界与注意事项**

- **超时只能中断异步等待**，无法中断同步死循环——`decide` 在主进程执行、不是沙箱，不要写阻塞代码
- **时区**：`ctx.now` 是宿主机的本地时间。服务器时区不是 UTC+8 时，`getHours()` 判断的"夜间"会整体偏移，务必像上面的示例那样用 `Intl.DateTimeFormat` 显式指定时区
- `ctx` **不含**后端健康状态、模型安装情况与资源占用；需要这些条件时由策略自行判断或改用配置开关

完整示例见 `policy.example.js`。

## 并发

每个后端有独立的 `max_concurrency` 闸门，防止 OCS 多线程搜题时把上游打爆。等待额度期间若整体预算耗尽则立即放弃。

排队请求被授予额度时计入 active，后续到达的请求继续服从同一并发上限。
